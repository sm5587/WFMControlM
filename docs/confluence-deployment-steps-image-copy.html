SQLite file permissions — required for Docker DB access:

The backend container runs as user node (UID 1000). The host file dev.db is bind-mounted into the container. If the file is owned by appadmin with mode 664, the container cannot write to it.

Use one of these before the first docker compose up:

  • Option A (simplest): chmod 666 ./data/sqlite/prisma/dev.db — no ownership change needed.
  • Option B (preferred long-term): sudo chown 1000:1000 ./data/sqlite/prisma/dev.db — must run with sudo; plain chown as appadmin fails with Operation not permitted.

If chown 1000:1000 fails even with sudo, stop Docker first (docker compose $COMPOSE down) — a running bind mount blocks ownership changes. See Part 5 — SQLite container write access.

Set at minimum in .env:

text LDAP_DEV_MOCK=false]]>

DATABASE_URL — do not misconfigure:

  • When you use both compose files (required), docker-compose.prod-hostdb.yml sets DATABASE_URL=file:./dev.db inside the container. You do not need to set DATABASE_URL in .env for production.
  • If you leave DATABASE_URL from .env.example (file:../../data/sqlite/prisma/dev.db), it is overridden by the hostdb compose file — that is OK.
  • Never set DATABASE_URL=./dev.db without the file: prefix — Prisma error P1013 (The provided database string is invalid).
  • Never copy a Windows absolute path from your dev machine into production .env.

Do not set REGISTRY or RELEASE_TAG — images use local tags from compose.

Part 5 — Troubleshooting

Prisma P1013 — invalid database connection string

Symptom: backend logs show Error: P1013: The provided database string is invalid. Error parsing connection string: ./dev.db

Cause: DATABASE_URL is missing the file: prefix (e.g. set to ./dev.db instead of file:./dev.db), or you started without docker-compose.prod-hostdb.yml.

bash

dev.db is a directory (not a file)

Symptom: ls -la ./data/sqlite/prisma/dev.db shows drwx (directory).

Cause: First docker compose up ran before touch ./data/sqlite/prisma/dev.db. Docker created the bind-mount target as a folder.

bash

SQLite container write access — chown: Operation not permitted

Symptom: chown: changing ownership of './data/sqlite/prisma/dev.db': Operation not permitted when running chown 1000:1000 as appadmin (without sudo).

Cause: Only root can assign file ownership to another user (UID 1000). The backend container runs as node (UID 1000) and needs write access to the bind-mounted dev.db.

bash

Success check: backend logs show Database connected successfully and No pending migrations to apply (not SQLite permission errors).

Permission denied on touch dev.db or mkdir

Symptom: touch: setting times of '/application/wfmwatch/data/sqlite/prisma/dev.db': Permission denied

Cause: Files under /application/wfmwatch are owned by another user (e.g. copied to /tmp as sm5587, or created with sudo without recursive chown).

Backend unhealthy / Missing critical AppConfig values

Symptom: Failed to start server: Missing critical AppConfig values: secrets.jwtSecret, secrets.jwtExpiresIn, infra.corsOrigins, infra.bodySizeLimit, engine.purgeSchedule

Cause: First-time seed not run yet, or seed ran but secrets.jwtSecret is still empty (DML seeds it blank by design).

Note: If logs show Could not decrypt secret "secrets.masterPasswordHash" on first install, that is usually harmless — ensure CONFIG_ENCRYPTION_KEY is set in .env before seed when possible.

sqlite3: command not found

Symptom: -bash: sqlite3: command not found when running step 2b.

Cause: The production server does not have the SQLite CLI installed (and you do not need it — Docker images already include Node + Prisma).

Fix: Use the backend container commands in step 2b above. Or install the CLI if you prefer: sudo dnf install -y sqlite (RHEL 9).

Frontend not starting — waits for backend healthy

Fix: Resolve backend first (docker compose $COMPOSE logs backend), then docker compose $COMPOSE up -d frontend.

DNS_PROBE_FINISHED_NXDOMAIN in Chrome (Windows laptop)

Symptom: Browser shows This site can't be reached / DNS_PROBE_FINISHED_NXDOMAIN for http://z182sp-usc1wstmon01:3015.

Cause: The short hostname is not resolvable from your PC. This is a DNS issue, not a failed deployment.

Fix:

  • Use http://z182sp-usc1wstmon01.rfx.zebra.com:3015 instead.
  • Confirm VPN is connected if required.
  • Until firewall opens ports 3015/4015, use the SSH tunnel in Part 4.2.
  • On the server, curl http://localhost:3015 should still work — that confirms the app is running.

Connection timeout from laptop (app works on server)

Symptom: FQDN resolves, but browser times out or connection is refused from your laptop; curl http://localhost:3015 on the server succeeds.

Cause: Corporate/GCP firewall blocking inbound TCP 3015 and 4015 to the server.

Fix: Ask IT to allow those ports from your network, or use the SSH tunnel (Part 4.2) until rules are in place.
