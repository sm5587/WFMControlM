WFM Watch — Job Monitoring and Alerting

What is WFM Watch?

WFM Watch is a web application that gives the WFM team one place to see job health across many client environments (75+). Instead of logging into servers one by one, operators use a single dashboard to:

  • See which scheduled jobs are due to run and whether they completed
  • Check batch job status in client databases
  • Get notified by email and in the app when jobs fail, run late, or miss deadlines
  • Track planned maintenance windows

WFM Watch has three main layers: a browser UI, an application server, and connections to existing WFM systems.

Security overview

This section summarizes how WFM Watch handles access, credentials, and external connections — intended for security review.

Access control

  • Login required — all monitoring and admin functions require an authenticated user.
  • Role-based access — admin settings (users, secrets, global config) are limited to authorized roles.
  • Session tokens — short-lived signed tokens; configurable expiry in Admin settings.
  • HTTP protections — security headers and CORS limited to approved front-end origins.

Data protection and encryption

WFM Watch protects sensitive data in three layers: encryption at rest for application secrets, one-way hashing for user passwords, and access controls so credentials are never exposed through the web UI.

Application secrets (SMTP, JWT, SSH)

Settings marked as secrets in Admin → Config are encrypted before they are written to the SQLite database.

SettingValue
AlgorithmAES-256-GCM (industry-standard symmetric encryption with authentication)
KeyCONFIG_ENCRYPTION_KEY — a 256-bit key set in the server environment at startup (not stored in the database)
Per-value randomnessA new random 12-byte initialization vector (IV) is generated for each secret when it is saved
Tamper detectionA 16-byte authentication tag (GCM) ensures encrypted values cannot be altered without detection
Stored formatBase64-encoded blob: IV + auth tag + ciphertext
At runtimeSecrets are decrypted in server memory only when needed; they are never sent to the browser

DB2 credentials (per client)

Each client’s DB2 host, database name, username, and password are stored in the Client table in SQLite. Passwords are encrypted at rest with AES-256-GCM (same algorithm and key as application secrets) before they are saved.

  • Admin-only updates — only users with Client Edit permission can change DB2 credentials.
  • Not exposed in the UI — the API returns a password is set indicator only; the actual password is never returned in client lists or dashboards.
  • Used only at connection time — passwords are decrypted in server memory and passed to a short-lived DB2 connector process when a monitoring query runs; they are not logged.

User login passwords

  • Stored as a bcrypt one-way hash (cannot be reversed to the original password).
  • Login uses signed JWT session tokens with configurable expiry.

Deployment (summary)

textTypical production layout
